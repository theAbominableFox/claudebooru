# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

szurubooru is an image board engine: a Python REST API (`server/`) and a vanilla-JS single-page client (`client/`). This checkout is a fork (`origin` = theAbominableFox/claudebooru, `upstream` = rr-/szurubooru).

## Development environment

Everything runs in Docker. `docker-compose.dev.yml` builds both `development` targets and bind-mounts `./server` and `./client` into the containers, so edits apply without rebuilding images:

```sh
docker compose -f docker-compose.dev.yml up --build -d   # app at http://localhost:${PORT} (8080)
docker compose -f docker-compose.dev.yml logs -f client  # client build/watch output
```

- Settings come from `.env` (Postgres credentials, `PORT`, `THREADS`, `BASE_URL`; see `doc/example.env`) and `server/config.yaml`, which is merged over `server/config.yaml.dist` (site name, secret, privileges, etc.). Both files are local and git-ignored.
- Server: `docker-start-dev.sh` runs `alembic upgrade head`, then serves `szurubooru.facade:app` with waitress under `hupper`, which reloads on Python changes.
- Client: `node build.js --watch` rebuilds on change and pushes a live-reload message over a websocket on port 8081. Templates (`html/*.tpl`) and styles (`css/*.styl`) are rebuilt by chokidar, and JS by watchify. If JS edits stop showing up in the served `js/app.min.js` while CSS still updates, the watchify watcher has stalled; restart the `client` container.
- nginx in the client container serves the built app at `/`, proxies `/api/*` to the server, and serves uploaded files from `/data/`.

## Commands

Server tests run in the `testing` Docker target, which starts its own throwaway Postgres via `testing.postgresql`. This mirrors CI (`.github/workflows/run-unit-tests.yml`):

```sh
docker build --target testing -t szuru-test ./server
docker run --rm -t szuru-test szurubooru/                                          # all tests
docker run --rm -t szuru-test szurubooru/tests/api/test_tag_creating.py -k some_name  # one file / test
```

The test files are copied into the image, so rebuild it after editing tests or code. The entrypoint is `pytest --tb=short`; extra arguments are passed through.

Lint and format runs through pre-commit (`.pre-commit-config.yaml`): black (line length 79) + isort + flake8 (`server/.flake8`, includes flake8-print, so no `print()`) for `server/`; prettier (`client/.prettierrc.yml`: 4-space indent, width 79) + eslint for `client/js/`.

```sh
pre-commit run --all-files
```

Client production build: `cd client && npm run build`, which writes to `client/public/`.

New DB migration: `doc/developer-utils/create-alembic-migration.sh <name>`. It generates the file in a throwaway container and copies it into `server/szurubooru/migrations/versions/`. Edit the generated file by hand; it is not autogenerated from models.

## Server architecture (`server/szurubooru/`)

Requests flow: `facade.py` (WSGI app, error mapping, startup tasks) → `rest/app.py` (route matching, `rest.Context`) → `middleware/` (authentication, cache purge, logging) → handler in `api/`.

- `api/*_api.py`: thin HTTP handlers registered with decorators from `rest/routes.py` (`@rest.routes.get("/tag/(?P<tag_name>.+)")`). They check privileges (`func.auth.verify_privilege`), call into `func/`, record `func.snapshots` for auditable changes, and return serialized dicts.
- `func/`: business logic per resource (tags, posts, users, pools…), plus `serialize_*` helpers. Validation errors raised here are mapped to HTTP errors in `facade.py`.
- `model/`: SQLAlchemy models; `db.py` holds the scoped `db.session`.
- `search/`: query parsing and execution. Each resource has a config in `search/configs/`, used through `search.Executor`.
- Privileges are named strings (e.g. `posts:edit:tags`) mapped to user ranks in `config.yaml.dist` → `privileges`. The client mirrors these through `api.hasPrivilege(...)`.
- REST API reference: `doc/API.md`.

Tests in `tests/` mirror the package layout. `conftest.py` provides factories (`user_factory`, `post_factory`, `tag_factory`…), `context_factory` for API calls, and `config_injector` for overriding config. Each test runs in a rolled-back transaction.

## Client architecture (`client/`)

No framework. Browserify + Babel bundle CommonJS modules from `js/`.

- `js/main.js` registers controllers. Each controller module calls `router.enter([...path], handler)` (`js/router.js`) and builds views.
- Layers: `controllers/` (route handling, API calls via `js/api.js`), `views/` (page rendering), `controls/` (reusable widgets: post content, sidebars, tag input, comments…), `models/` (event-emitting data objects; `settings.js` is localStorage-backed), `util/views.js` (DOM helpers, template context helpers such as `makeThumbnail`, `makeCheckbox`).
- Templates: `html/*.tpl` are underscore templates with `ctx` as the variable, loaded with `views.getTemplate("file-name")`. `build.js` compiles them into `js/.templates.autogen.js` (generated, don't edit). They use `<!-- -->` comments between tags to avoid whitespace text nodes.
- Styles: Stylus in `css/`; every file `@import colors`. The accent color is a runtime CSS variable: `$main-color` is `var(--accent-color)`, set by `js/util/theme.js` from settings. Don't apply Stylus color functions (`lighten`, `rgba`, `mix`) to it, because they fail on a `var()`. Use the `color-mix()` helpers in `css/colors.styl` (`$main-color-hover-background`, `$main-color-glow`) or write `unquote('color-mix(...)')`. Shared corner rounding is `$ui-border-radius`.
- Dark theme: `body.darktheme`, toggled live by `js/util/theme.js`. Most stylesheets have a parallel `.darktheme …` block next to the light rules.
- Post page (`html/post_main.tpl`, `css/post-main-view.styl`) uses a CSS grid with `display: contents` on the sidebar wrappers. Edit mode (`.post-view.edit-mode`) uses a different grid. Post sizing (fit modes) is computed in `js/views/post_main_view.js` / `js/controls/post_content_control.js` from the viewport and the layout around the post.
